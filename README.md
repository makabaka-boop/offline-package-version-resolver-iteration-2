# 离线软件包依赖求解器

一个只使用 Python 标准库的命令行/容器求解器。它读取一份离线目录 JSON，输出满足根需求、依赖闭区间约束与已知冲突互斥约束的完整可安装集合；若不存在这样的集合，只输出 `UNRESOLVABLE`。

## 目录限制

- 最多 10 个唯一包名；包名必须为非空、可见 ASCII 字符（不含空格）。
- 每个包有 1～4 个正整数版本。
- 每个版本可声明 0 个或多个依赖，依赖要求为闭区间 `[lower, upper]`。
- 根需求也使用闭区间。
- 可选 `conflicts` 声明已知不兼容的精确版本组合：每项为 `[[包名, 版本], [包名, 版本]]`，两个端点必须是目录内**不同**包的**已知**版本；整份列表不得有重复（含逆序重复）。
- 冲突是双向互斥约束：两个端点版本不得同时出现在最终集合中。它不产生依赖，也不会把闭包外的包保留下来。
- 依赖环允许；环上每个被选版本必须被所有入边区间接受。
- 最终集合必须**恰为**根需求沿所选版本依赖可达的闭包：不能缺少被依赖包，也不能保留闭包外的已装包。

## 优化目标（按优先级）

在所有可行解中依次选择：

1. **变更包数最少**：相对 `installed`，新增、删除、改版都算 1 个包。
2. **最终包数最少**。
3. **版本向量字典序最大**：按目录中全部包名排序，未安装位置记作版本 `0`。

例如目录名顺序为 `("a", "b")` 时，只安装 `b=2` 的向量是 `(0, 2)`。

`installed` 中允许出现目录里已经不存在的版本号（视为过期安装，升级或删除算一次变更）；但 `installed` 中的包名、根需求包名和依赖包名都必须在目录内，否则按格式错误直接拒绝。根需求为空对象是合法输入，表示目标闭包为空，当前已装包都应删除。

## 输入格式

```json
{
  "packages": {
    "app": {
      "1": {"dependencies": {"lib": [1, 2]}},
      "2": {"dependencies": {}}
    },
    "lib": {
      "1": {"dependencies": {}},
      "2": {"dependencies": {}}
    }
  },
  "root": {
    "app": [1, 2]
  },
  "installed": {
    "app": 1
  },
  "conflicts": [
    [["app", 2], ["lib", 1]]
  ]
}
```

- `packages`、`root`、`installed` 三个顶层字段均为必填，`conflicts` 可省略或为空数组；不允许未知字段。
- `dependencies` 可省略或为空对象。
- 版本键必须是无符号正整数的十进制字符串（如 `"1"`，不接受 `"01"`、`"1.0"`）。
- 区间必须是恰好两个整数组成的数组，且满足 `1 <= lower <= upper`。
- 每个 `conflicts` 端点是 `[包名, 版本]` 二元数组；版本为整数，且必须是该包在目录中的已知版本（与 `installed` 不同，不接受过期版本）。
- 布尔值不会被当作整数接受；JSON 重复对象键会被拒绝。

## 输出与退出码

- 有解：标准输出打印一个 JSON 对象，键按包名字典序排列，如 `{"app": 2, "lib": 2}`；退出码 `0`。
- 无解：标准输出打印一行 `UNRESOLVABLE`；退出码 `0`。不会输出部分计划。根需求与冲突共同导致无解时也只输出该标记。
- JSON/契约格式错误、目录外依赖、未知或同包冲突等非法 `conflicts`：错误信息写入标准错误；退出码 `2`；标准输出不产生计划。

## 根需求放宽模式（需显式启用）

当多条根需求合在一起无解时，默认仍只输出 `UNRESOLVABLE`。加上 `--relax-roots` 后，求解器改为给出一份**可安装的最小让步方案**：

- 只允许暂时**撤销整条根需求**；不得改写依赖、冲突、根区间或已装版本。被撤销根的包若仍被保留需求沿依赖闭包到达，照常出现在结果中。
- 撤销集合按以下顺序择优（与保留需求最终闭包的好坏无关）：
  1. 撤销条数最少；
  2. 并列时按“被撤销包名排序后的列表”字典序最小裁决。
- 对保留下来的根需求，仍按原三级目标（最少变更、最少包数、最大版本向量）求完整闭包。
- 对任一被撤销的根需求，把它单独加回保留集合后仍应无解——因此让步确有必要（测试通过全组合枚举复核这一点）。
- 搜索每个候选撤销集时都从全新的约束传播/分支状态开始，状态不会跨根集合泄漏。
- 撤销全部根时闭包为空恒有解，因此已通过契约校验的请求在该模式下必有方案。

标准输出打印一个含三个键的 JSON 对象：

- `revoked`：被撤销根需求的包名列表（字典序）。
- `selection`：最终安装集合，`包名 -> 版本`。
- `changes`：相对 `installed` 的逐项变化，按包名字典序排列；每项为
  `{"name": 包名, "from": 旧版本或 null, "to": 新版本或 null, "kind": "added"|"removed"|"changed"}`。
  `added` 表示原未装现安装，`removed` 表示原安装现删除，`changed` 表示版本变更（含过期已装版本升级）。

退出码：成功输出方案为 `0`；JSON/契约格式错误仍为 `2` 且标准输出为空（格式错误不会被包装成无解，也不会输出部分计划）。原请求本身有解时，`revoked` 为空、`selection` 即普通最优解。

```bash
PYTHONPATH=src python3 -m resolver --relax-roots examples/relax.json
# {"changes": [{"from": null, "kind": "added", "name": "c", "to": 1}],
#  "revoked": ["b"], "selection": {"a": 1, "c": 1}}
```

未加 `--relax-roots` 时，标准输出、退出码与求解结果与旧版逐字兼容。

## 本地运行

```bash
# 从标准输入读取
PYTHONPATH=src python3 -m resolver < examples/request.json

# 或传入文件路径
PYTHONPATH=src python3 -m resolver examples/request.json

# 带已知冲突的示例
PYTHONPATH=src python3 -m resolver examples/conflicts.json

# 根需求放宽模式（撤销最少的整条根需求）
PYTHONPATH=src python3 -m resolver --relax-roots examples/relax.json
```

## Docker Compose

```bash
# 构建
docker compose build resolver

# 通过标准输入运行
docker compose run --rm resolver < examples/request.json

# 或挂载文件并传路径
docker compose run --rm -v "$PWD:/work" resolver /work/examples/request.json
```

## 测试

测试中的“对拍”会对小目录枚举每个包的“不安装/选择某个版本”的全部组合，执行根可达闭包、冲突互斥和全部区间检查，再按相同目标选出答案，与回溯求解器结果逐一比较。覆盖：

- 3 包 × 最多 3 版本、5 包 × 最多 4 版本的随机小目录：无冲突 90 个、带随机 `conflicts` 90 个；
- 自环、互相依赖环、冲突区间、空根；
- 冲突强制回退版本、冲突贯穿依赖传播、环内冲突、冲突与过期已装版本并存；
- 删除不再可达的包、过期已装版本、包数 tie-break、完整目录向量字典序；
- CLI 成功、`UNRESOLVABLE` 和格式错误退出码。

根需求放宽模式（`tests/test_relaxed.py`、`tests/test_relaxed_cli.py`）额外对小目录做全组合枚举：按“撤销条数、撤销包名字典序”枚举撤销集，对首个可解集再用上述对拍求保留需求的最优闭包，分别核对**撤销集、闭包与三级目标**；并复核把任一被撤销根单独加回仍无解（让步必要性）。覆盖依赖环、冲突、过期已装版本、被撤销根仍作为依赖保留、同名次撤销集的字典序裁决、重复求解的状态隔离，以及 `--relax-roots` 下格式错误仍退出 `2` 且不输出部分计划。

有 pytest 时：

```bash

# 或使用 Compose（容器内安装 pytest）
docker compose run --rm test
```

在没有 pytest、也不能联网安装的环境中，仓库提供了仅用于本测试集的标准库兼容运行器：

## 算法说明

求解器使用约束传播 + 深度优先回溯：

- 对每个已被根或依赖要求的包维护交集区间（所有下确界取 max、上确界取 min）。
- 每选一个版本，立即加入其依赖边；若区间变为空，或与已选依赖版本冲突，则回滚。
- 选择版本时同步查询 `conflicts` 双向互斥表：与任何已选版本构成已知冲突的候选直接跳过；冲突在搜索过程中检查并随回溯撤销，而不是先求出旧最优再删除冲突包。
- 待选包采用“可行版本最少优先”（MRV）以尽早发现冲突。
- 分支内版本从大到小尝试，以便先找到字典序较大的候选。
- 分支定界使用安全下界：
  - 当前必选包中无法保持已装版本的数量；
  - 当前闭包大小；
  - 乐观版本向量上界。
  这些剪枝只排除不可能优于当前最优解的分支，不改变穷举语义。

根需求放宽模式在此之上做一层枚举：按撤销条数从小到大、同条数按撤销包名列表字典序，依次把候选根集合交给求解器；每个候选都用独立的一份传播/回溯状态求解（保留根区间作为初始 `bounds`），取第一个可行候选的最优闭包。由于根最多 10 条，撤销集最多枚举 2^10 = 1024 个，且按条数顺序一旦命中即返回。

目录上限只有 10 包 × 4 版本（约一百万组合量级），最坏无依赖情形下纯穷举约 6 秒；加入上述剪枝后典型/边界基准为毫秒级。
